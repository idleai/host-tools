# Protocol v1 reference

These rules apply to clients, Evo, and standalone or managed coordination
providers using `idle_protocol::v1`. Package version `0.1.0` and wire version `"1"`
are separate: every request, response, runtime report and retained event requires
`api_version: "1"`.

See the [JSON Schema](../schemas/v1.json) for message shapes and the
[fixtures](../tests/fixtures) for concrete wire examples.

## Wire compatibility

Messages use JSON. Field names and type labels use `snake_case`, such as
`workspace_id` and `submit_input`. Each handler reads the request or response type
it expects. `WireMessage` groups these types for schema generation; it adds no
wrapper to messages. Each implementation chooses how messages are sent, which
URLs to use, if any, and how callers authenticate.

Receivers can ignore extra optional fields. They must reject unknown protocol
versions, enum values and operations. If a client cannot read an event, it must
leave its recovery position unchanged.

Adding a required field, changing an existing meaning or adding an enum value
needs a new protocol version, unless both sides explicitly agree to support the
change. Keep the Rust types, JSON examples and schema in sync.

IDs are nonempty, case-sensitive strings. Keep them exactly as issued. Do not
interpret their contents or build them from display names, host labels, file
paths or usernames that can change. Services reject empty IDs and check that
referenced resources exist in the correct scope. `ChainRef` carries a reference
issued by EditChain. EditChain owns its record format; workspace metadata stays
outside the engine.

Revisions, Control epochs, event positions, input order and timestamps are sent as
JSON strings: `"42"` instead of `42`. This keeps large numbers exact in JavaScript.
Only digits are allowed, from `"0"` through `"18446744073709551615"`, with no
leading zeros except `"0"` itself.

Revisions, input order and assigned Control epochs start at `"1"`. An event
position of `"0"` marks the starting boundary; a Control epoch of `"0"` means no
owner has been assigned. Timestamps are milliseconds since January 1, 1970 UTC.
Use the appropriate revision, position or order field to compare updates;
timestamps do not establish their order.

## API surface

`Request<Command>` performs a mutation and returns `Response<CommandResult>`.
`Request<Query>` returns `Response<QueryResult>`. Responses echo the complete
original request key, including scope and contributor. Errors have a stable code,
safe message and explicit retry advice.

Evo receives `RuntimeSubmission` directly or from a coordination forwarder and
returns `Response<RuntimeInputUpdate>`. Forwarded submissions include the original
`BackendReceipt`; direct submissions omit it. Later confirmations can arrive as
`RuntimeReport` or retained events without keeping the submitter connected.

| Domain | Commands | Reads and retained events |
| --- | --- | --- |
| Workspace | Put metadata/repository bindings using a write precondition | Snapshot; `workspace_changed` |
| Membership | Invite, accept/revoke invitation, change role, revoke member | Snapshot; contributor/membership/invitation changes |
| Sessions | Put directory metadata; submit attributed input | Snapshot, input status; session changes and runtime input updates |
| Resources | Put hosts/providers/models; detach workspace binding | Snapshot; publication/health changes and removal tombstones |
| Grants | Issue/revoke separate session, compute or provider grants | Snapshot; `grant_changed`, including revocation |
| Control | Acquire, renew, release | Ownership/validation queries; `control_changed` |
| Recovery | Stable mutation IDs | Request status, snapshot and bounded catch-up |

Sessions are either `Runner` or `Control` (`runner` or `control` on the wire).

Writes use `Absent` for creation or the last observed revision for replacement.
Authorities atomically check the precondition, authorize, assign the next revision
and persist the change, retained events and deduplication result. Revisions must
not reset across deletion/recreation. New workspace creation also establishes its
authenticated creator's owner membership. Updating a workspace cannot change its
chain identity. Changing a session binding cannot reset its identity or input order.
Publishing directory metadata never starts a session, installs a model or executes
a host operation; those remain runtime operations.

## Identity and retry semantics

`ContributorIdentity` is attribution, **not an authentication credential**. The
receiver verifies its immutable issuer/subject and contributor mapping against the
authenticated connection. A forwarder uses an authenticated delegation channel and
preserves the original contributor; it must not replace the author with the session
owner, compute owner or relay identity. Standalone peer authentication can resolve
the same shape without managed sign-in. Model-provider credentials are independent.

The mutation deduplication key is `(workspace_id, contributor_id, request_id)`
across all command kinds. Generate it before first submission and retain it through
timeouts, reconnects and forwarding. Before executing anything, the authority:

1. Authenticates the caller and checks current access to this workspace/result.
2. Resolves an existing key: identical recognized semantic content returns the
   original durable result; different command, identity assertion, deadline, fence
   or payload returns `idempotency_conflict`, with no additional effects.
3. For a new key, rejects a passed `expires_at` deadline using the authority clock,
   then authorizes and durably records the operation/result atomically.

JSON key ordering/whitespace are not semantic differences. Authentication tokens
are not part of the payload. Concurrent duplicates resolve to one durable request;
Evo deduplicates the same key again at runtime acceptance. A retry must not allocate
another delivery order or repeat side effects. Replaying an old receipt does not
renew a lease or prove that old grants are still effective.

`BackendReceipt.retry_until` guarantees result retention at least through the
original first-receipt deadline. An expired key with no retained result is rejected,
never executed as new work. Deadline changes require a new logical operation and
key. `RequestStatus::Unknown` does not establish whether execution happened.
Reconcile uncertain outcomes before issuing a replacement request.

The first-receipt deadline does not cancel durably queued work. Forwarded input
includes the unchanged original context and durable receipt over the trusted
adapter channel; Evo may accept it after that deadline, but still checks current
permissions and fences. Direct submissions with no earlier receipt apply the
deadline at their receiving authority. Detachment does not cancel running work.

## Receipt versus runtime state

| Message | Authority | What it proves |
| --- | --- | --- |
| `CommandResult::Received` / `BackendReceipt` | Coordination provider | Request and forwarding record are durable |
| `CommandResult::Committed` | Coordination provider | Metadata, retained events and retry result committed atomically |
| `RuntimeInputState::Accepted` | Authenticated Evo runtime | Attributed input durably accepted |
| `Ordered` / `Delivery` | Evo | Unique session-wide delivery order durably assigned |
| `Running` | Evo | Processing started |
| `Completed` | Evo | Explicit success, failure or cancellation confirmed |
| `Rejected` | Evo | Input declined before acceptance; no order assigned |

Only `SubmitInput` returns `Received`; metadata operations return `Committed`, and
Control mutations return `Control` with both commit and resulting ownership.
`RuntimeReport`, `QueryResult::InputStatus` and `EventBody::InputUpdated` carry the
same runtime fact. Receivers authenticate the producing runtime against the session
binding and check workspace, request key and contributor consistency before using it.

Runtime input revisions increase per input. Delivery order increases across the
entire session, including all contributors, restarts and runtime relocation. Its
meaning is delivery order, not wall-clock order or completion order. Accepted inputs
eventually reach an ordered terminal outcome, even if cancelled before execution.
Observers can skip intermediate states, but cannot regress a revision, overwrite
terminal state, change an assigned order or substitute a contributor. A conflicting
fact at the same revision is a protocol error, not a last-write-wins update.

## Scope, grants and fencing

References and grants belong to the request's workspace, including for resources
shared across workspaces. Standalone and managed modes share this protocol;
standalone has one repository. Moving to managed mode preserves IDs, input order,
Control epochs and retry records through their retention window. Reject old
requests whose outcomes cannot be recovered.

Membership, session, host and provider permissions are independent. Resource
listings grant no access. Services and runtimes enforce current permissions,
sandbox limits and agent rules on operations, subscriptions and open connections.
Membership revocation overrides workspace grants; revoked or expired grants stop
authorizing access.

Only one Control lease can be active per workspace. Acquisition atomically checks
the expected epoch and absence of an unexpired lease, then increases the epoch.
Renewal requires the current, unexpired holder and keeps its epoch. Release keeps
`last_epoch`; reacquisition increases it. Epochs never reset or wrap; exhaustion
is an error.

Every Control action or history write carries a `ControlFence`. Check the
authenticated holder, workspace, epoch and expiry using the authority's clock at
execution and history append time. These checks must be atomic with takeover so
stale owners cannot act or write. Cached validation cannot authorize later effects.

## Recovery

`RecoveryCursor` bookmarks one authenticated contributor's workspace event stream:
`(workspace_id, contributor_id, stream_id, position)`. Compare positions only within
the same scope; reject cursors for another workspace/contributor or a future position.

1. Replace local state with an authorized, consistent snapshot at `as_of`.
2. Fetch events strictly after the cursor. Pages echo `after`, contain increasing
   positions and give a same-scope `through`, including filtered positions.
3. Apply the whole page before saving `through`; continue while `has_more`.
   Unknown events or failures leave the cursor unchanged.
4. Ignore identical duplicates by event identity/position and reconcile updates by
   entity revision. Conflicting duplicates are errors.

Resume live delivery after catch-up, allowing overlap and out-of-order arrivals.
Neither live events nor commit receipts justify skipping unapplied positions.
Timestamps never replace cursors; keep producer and recording times separate.

Expired history or changed streams/visibility require `SnapshotRequired`. Fetch
a fresh authorized snapshot and cursor, replacing the old view and removing newly
hidden data. Expired history must never appear as an empty successful page.
Revoked workspace access returns `Forbidden` and closes subscriptions.

Snapshots preserve session identities and show the last confirmed runtime state.
Disconnected hosts remain unavailable/unknown; recovery cannot imply new progress.
